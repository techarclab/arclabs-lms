3.1

RS-485 physical layer

You will learn
  • The electrical limits of RS-485: voltages, unit loads, cable length
  • Why termination and biasing are needed, and where they go
  • How to wire a MAX3485 to the ESP32-C3, and how to fault-find a bus

RS-485 defines only the electrical layer: voltages, drivers and receivers on a twisted pair. It says nothing about bytes or messages. Modbus RTU, many meters and drives run their own protocols on top of it.

Termination

A twisted pair has a characteristic impedance of about 120 Ω. When a signal reaches an unterminated cable end, it reflects back and corrupts the following bits. A 120 Ω resistor at each of the two physical ends absorbs the signal instead. Terminators at every node would overload the drivers.

Biasing (fail-safe)

In half-duplex RS-485, there are moments when no driver is active, for example while the master waits for a reply. The lines then float, and receivers can read noise as start bits. Bias resistors hold the bus in the idle (logic 1) state: D1 pulled up to +5 V and D0 pulled down to 0 V. The Modbus specification gives values between 450 Ω and 650 Ω, fitted once per bus, usually at the master. Many USB adapters and modules already include bias and termination resistors, sometimes switchable; check before adding more.

The A/B naming trap

The TIA-485 standard calls the inverting line A and the non-inverting line B, but many module makers print the opposite. If a bus never answers, swap the two data wires as a first test; this cannot damage RS-485 transceivers.

3.2

Modbus RTU

You will learn
  • The Modbus data model and why addresses are off by one
  • The RTU frame, function codes, exception responses and CRC-16
  • Frame timing, and how long a polling cycle takes

Modbus (1979) is the most widely used field protocol because it is simple, open and free. A single master asks, and slaves answer. A slave never speaks unless it is asked. (Newer documents call them client and server.)

The data model

The off-by-one trap

On the wire, addresses start at 0. Manuals usually number from 1 with a type prefix. So “holding register 40001” is sent as function 03, address 0; “40108” is address 107. Most “wrong value” problems in the lab are this.

Worked examplereading two input registers

The master asks slave 1 for 2 input registers starting at address 0 (30001–30002):

Request: 01 04 00 00 00 02 71 CB

addr 01 · function 04 · start 0000 · quantity 0002 · CRC 71 CB (low byte first). The slave replies:

Response: 01 04 04 00 FA 01 C2 5B B4

byte count 04 · register 0 = 0x00FA = 250 → 25.0 °C (scaled × 10) · register 1 = 0x01C2 = 450 → 45 % RH.

Exception responses

If a slave cannot do what was asked, it returns the function code with the top bit set (function + 0x80) and an exception code. If it receives a corrupt frame (bad CRC), it stays silent, and the master times out.

CRC-16

Every RTU frame ends with a 16-bit cyclic redundancy check computed over all preceding bytes: polynomial 0xA001 (reflected 0x8005), initial value 0xFFFF, low byte sent first. The receiver recomputes it and silently discards the frame on a mismatch.

modbus_crc16.c
uint16_t modbus_crc16(const uint8_t *buf, size_t len) {
  uint16_t crc = 0xFFFF;
  for (size_t i = 0; i < len; i++) {
    crc ^= buf[i];
    for (int b = 0; b < 8; b++)
      crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : crc >> 1;
  }
  return crc;   // send (crc & 0xFF) first, then (crc >> 8)
}

Timing

RTU frames have no start or end marker. Instead, a frame ends when the line has been silent for 3.5 character times (t3.5), and gaps inside a frame must be shorter than 1.5 characters (t1.5). One RTU character is 11 bits: start, 8 data, parity, stop (or 2 stop bits when there is no parity). Above 19200 baud the specification fixes t3.5 at 1.75 ms and t1.5 at 0.75 ms.

Worked examplehow long does a polling cycle take?

9600 baud, read 2 registers from each of 20 slaves, assume 5 ms slave turnaround.

Character time = 11 ÷ 9600 = 1.146 ms · t3.5 = 4.01 ms
Request 8 bytes = 9.17 ms · Response 9 bytes = 10.31 ms
Per slave ≈ 9.17 + 5 + 10.31 + 4.01 ≈ 28.5 ms → 20 slaves ≈ 0.57 s per scan

A dead slave costs a full response timeout (often 1 s) on every scan, which is why masters stop polling offline slaves for a while.

A 32-bit float or counter uses two consecutive registers. Bytes inside a register are big-endian, but the order of the two registers is not standardised: some devices send the high word first (“ABCD”), others the low word first (“CDAB”). The device's register map tells you which; if a value looks absurd, try swapping words.

Parity

The Modbus specification's default is 8E1 (even parity), but many devices ship as 8N1. Master and slave must match exactly. Your ESP32 lab uses 8N1.

Security

Modbus has no authentication and no encryption. Anyone who can reach port 502 can read every register and switch every coil. 3.5

CAN bus and CAN FD

You will learn
  • The CAN physical layer and frame
  • Bitwise arbitration: why the lowest ID always wins
  • Error handling, bus-off, and what CAN FD adds

CAN (Controller Area Network) was designed by Bosch for cars and is now used in machines, robots and medical equipment. It is multi-master: any node may transmit when the bus is free, and collisions are resolved by message priority without losing any data.

The bus has two states. Dominant (logic 0): CAN_H ≈ 3.5 V, CAN_L ≈ 1.5 V. Recessive (logic 1): both ≈ 2.5 V. If any node drives dominant, the whole bus is dominant; this “wired-AND” behaviour is what makes arbitration work.

The classic CAN frame

Frame types: data frame, remote frame (request for data), error frame (sent by any node that detects an error), and overload frame (asks for extra delay).

Bitwise arbitration

When two nodes start at the same moment, each sends its identifier bit by bit, most significant first, while listening to the bus. A node that sends recessive (1) but reads dominant (0) knows a higher-priority message is on the bus; it stops and becomes a receiver. The winner's frame continues undamaged. So the lowest identifier has the highest priority, and no bandwidth is lost to collisions.

CAN arbitration simulatorThree nodes start transmitting together

0 = dominant, 1 = recessive. The bus is the AND of every active transmitter. Red marks the bit where a node lost.

Error handling

  • Five checks: bit monitoring (a node reads back what it sends), bit stuffing (after five identical bits a complementary bit is inserted, so a sixth identical bit is an error), CRC, form check of fixed fields, and ACK (at least one receiver must acknowledge).
  • Each node keeps a transmit (TEC) and receive (REC) error counter. Error-active → error-passive when a counter exceeds 127 → bus-off when TEC exceeds 255. A bus-off node disconnects itself so a faulty node cannot jam the bus, and may rejoin after 128 occurrences of 11 recessive bits.

CAN defines only the frame. Higher-layer protocols define what the IDs and bytes mean: CANopen (machines, CiA 301), J1939 (trucks and off-highway, 29-bit IDs) and DeviceNet.

3.6

Metering protocols: DLMS/COSEM and M-Bus

You will learn
  • How DLMS/COSEM (IEC 62056) models a meter
  • How to read an OBIS code
  • Where M-Bus and wireless M-Bus fit

Utility meters have special needs: billing-grade accuracy, tamper evidence, legal metrology, 15-year life and often battery power. They use dedicated protocols.

DLMS/COSEM (IEC 62056)

  • DLMS (Device Language Message Specification) is the application-layer protocol: how to get, set and act on data.
  • COSEM (Companion Specification for Energy Metering) is the object model: every quantity is an object of a standard interface class, such as Data (1), Register (3), Profile Generic (7, load profiles) and Clock (8).
  • Each object is identified by an OBIS code.
  • Clients connect through associations with different rights: a public client (no security, basic reads), low-level security (password), and high-level security (HLS, cryptographic authentication and encryption).
  • Transports: optical port (IEC 62056-21, for hand-held reading), HDLC over RS-485 or optical, and a TCP/UDP wrapper over cellular or Ethernet. India's smart-meter companion standard is IS 15959.

M-Bus and wireless M-Bus (EN 13757)

  • M-Bus (Meter-Bus): two-wire bus for heat, water and gas meters. The master powers the meters over the bus, the wiring is polarity-independent, and typical speeds are 300–9600 baud (2400 is common).
  • Wireless M-Bus (EN 13757-4): battery meters transmit short telegrams, at 868 MHz in Europe, to a collector or a walk-by / drive-by reader.

Time synchronisation: PTP, gPTP and TSN

You will learn
  • Why plants need synchronised clocks
  • How PTP calculates offset and delay from four timestamps
  • What gPTP and TSN add for deterministic networks

When a trip happens, you need to know which event came first, even if they were recorded by different devices. Motion axes must move in step, and TSN switches open their gates on a shared schedule. All of this needs clocks that agree.

Protocol gateways and selection

You will learn
  • What a protocol gateway must do beyond copying values
  • How to choose a protocol for a given job

Real plants mix generations of equipment. A gateway translates between them, for example Modbus RTU meters to an OPC UA server, which is exactly what you build in Lab 5.

Mapping

Register → named tag, scaling (÷ 10), data type, word order, engineering units.

Quality and time

Mark values bad or stale when the source stops answering. Record whether the timestamp is from the source or the gateway.

Rate and load

Poll no faster than the source and bus can handle; one gateway often serves many clients.

Security boundary

The gateway is often the only device that touches both networks. Expose only what is needed, read-only where possible.

4.4

MQTT fundamentals

You will learn
  • Publish/subscribe and the broker's role
  • Topic design and wildcards
  • QoS 0/1/2, retained messages, Last Will, keep-alive and sessions

MQTT is a lightweight publish/subscribe protocol over TCP. Devices never talk to each other directly: they publish messages to topics on a broker, and the broker forwards each message to every client subscribed to that topic. Port 1883 plain, 8883 with TLS.

Topics and wildcards

  • + matches exactly one level. # matches any number of levels and must be the last character, on its own level.
  • Topics are case-sensitive. Avoid a leading “/” (it creates an empty first level) and spaces.
  • Topics starting with $ (such as $SYS/ broker statistics) are not matched by a filter that starts with a wildcard.
  • Wildcards are for subscribing only; you always publish to a full topic.
MQTT topic matcherEdit the filter or the topics

Quality of Service

QoSGuaranteeUse for
0At most once; no acknowledgementFrequent telemetry where the next sample replaces a lost one
1At least once; resent until PUBACK; duplicates possibleAlarms, events, commands with idempotent handling (most IIoT data)
2Exactly once; four-step handshakeRare: counters or billing events where duplicates are unacceptable

A subscriber receives a message at the lower of the publish QoS and its subscription QoS. A QoS 2 message to a QoS 0 subscription arrives as QoS 0.

Retained messages, Last Will, keep-alive and sessions

FeatureHow it worksTypical use
Retained messageThe broker stores the last retained message on a topic and sends it immediately to every new subscriber. Publish an empty retained message to clear it.Current status, last known value, configuration
Last Will and Testament (LWT)Set in CONNECT. The broker publishes it if the client disappears without a clean DISCONNECT (keep-alive timeout, network loss).Retained offline on the status topic
Keep-aliveClient sends PINGREQ when idle. The broker drops it after 1.5 × the keep-alive interval with no traffic.Detecting dead devices; triggers the LWT
Persistent sessionClean session false (3.1.1) or Clean Start false with a session expiry (MQTT 5). The broker keeps subscriptions and queues QoS 1/2 messages while the client is offline.Command topics for devices that sleep or roam
The presence pattern

At connect, set the LWT to offline (retained) on …/status, then publish online (retained) to the same topic. Any dashboard that subscribes later instantly sees whether each device is up.

Common lab bug

Every client needs a unique client ID. When a second client connects with the same ID, the broker disconnects the first. Two boards with copied code will keep kicking each other off.

Alarm management (ISA-18.2)

You will learn
  • What counts as an alarm, and what does not
  • Alarm states, acknowledgement, shelving and suppression
  • Priorities, nuisance alarms, floods, and the performance targets

ANSI/ISA-18.2 (and IEC 62682) defines an alarm as an audible and/or visible means of telling the operator about an equipment malfunction, process deviation or abnormal condition that requires a response. If no action is needed, it is an event or a message, not an alarm.

Why it matters

Investigations into major incidents, such as the 1994 Texaco Milford Haven explosion, found operators buried under hundreds of alarms in the minutes before the accident. An alarm system that cries wolf is ignored when it matters.

TermMeaning
AcknowledgeThe operator confirms they have seen the alarm. It does not clear the condition.
ShelvingOperator-initiated, temporary removal from view, with a time limit and logging. Used for a known nuisance alarm, for example during maintenance.
Suppressed by designLogic hides alarms that are meaningless in the current state, for example low-flow alarms when the pump is deliberately stopped.
Out of serviceRemoved for maintenance through a controlled, authorised process.
PriorityBased on consequence and time available to respond. A common distribution target is about 80 % low, 15 % medium, 5 % high.

DHT dht(5, DHT11);
ModbusRTU mb;

void setup() {
  Serial.begin(115200);                                 // USB debug console
  Serial1.begin(9600, SERIAL_8N1, RS485_RX, RS485_TX);  // RS-485 side
  mb.begin(&Serial1, RS485_DE);    // library raises DE while transmitting
  mb.slave(SLAVE_ID);
  mb.addIreg(0, 0, 2);             // IR 0-1: temperature x10, humidity
  mb.addHreg(0, 500);              // HR 0: alarm threshold x10
  dht.begin();
}

void loop() {
  mb.task();                       // call as often as possible
  static uint32_t last = 0;
  if (millis() - last >= 2000) {  // DHT11: at most one read per second
    last = millis();
    float t = dht.readTemperature(), h = dht.readHumidity();
    if (!isnan(t) && !isnan(h)) {
      mb.Ireg(0, (uint16_t)(int16_t)lroundf(t * 10));
      mb.Ireg(1, (uint16_t)lroundf(h));
      if (t * 10 > (int16_t)mb.Hreg(0)) Serial.println("Temperature above threshold");
    }
  }
}

import asyncio
from asyncua import Server
from pymodbus.client import AsyncModbusTcpClient

ESP32_IP = "192.168.1.50"      # printed by Lab 4

def signed(v):                  # 16-bit register -> signed int
    return v - 65536 if v > 32767 else v

async def main():
    server = Server()
    await server.init()
    server.set_endpoint("opc.tcp://0.0.0.0:4840/arc/gateway/")
    server.set_server_name("ARC Lab Modbus-OPC UA Gateway")
    idx = await server.register_namespace("urn:arclabs:lab5")

    node   = await server.nodes.objects.add_object(idx, "ESP32C3_Node")
    temp   = await node.add_variable(idx, "Temperature", 0.0)
    hum    = await node.add_variable(idx, "Humidity", 0.0)
    flame  = await node.add_variable(idx, "FlameDetected", False)
    online = await node.add_variable(idx, "SourceOnline", False)

    modbus = AsyncModbusTcpClient(ESP32_IP, port=502, timeout=2)

    async with server:
        while True:
            try:
                if not modbus.connected:
                    await modbus.connect()
                ir = await modbus.read_input_registers(0, count=2)
                di = await modbus.read_discrete_inputs(0, count=2)
                if ir.isError() or di.isError():
                    raise IOError("Modbus exception response")
                await temp.write_value(signed(ir.registers[0]) / 10.0)
                await hum.write_value(float(ir.registers[1]))
                await flame.write_value(bool(di.bits[0]))
                await online.write_value(True)
            except Exception as e:
                print("read failed:", e)
                await online.write_value(False)   # tell clients the data is stale
            await asyncio.sleep(1)

PubSubClient mqtt(net);
DHT dht(5, DHT11);

String topic(const char* leaf) { return String(BASE) + "/" + leaf; }

void onMessage(char* t, byte* payload, unsigned int len) {
  Serial.printf("command on %s: %.*s\n", t, len, (char*)payload);
}

void connectMqtt() {
  while (!mqtt.connected()) {
    // Last Will: retained "offline" if we vanish without DISCONNECT
    if (mqtt.connect(DEVICE_ID, topic("status").c_str(), 1, true, "offline")) {
      mqtt.publish(topic("status").c_str(), "online", true);   // retained presence
      mqtt.subscribe(topic("cmd/#").c_str(), 1);
    } else {
      Serial.printf("MQTT connect failed, state %d\n", mqtt.state());
      delay(2000);
    }
  }
}

void setup() {
  Serial.begin(115200);
  WiFi.begin("ARC-LAB", "********");
  while (WiFi.status() != WL_CONNECTED) delay(250);
  mqtt.setServer(BROKER, 1883);
  mqtt.setCallback(onMessage);
  dht.begin();
}

void loop() {
  if (!mqtt.connected()) connectMqtt();
  mqtt.loop();
  static uint32_t last = 0;
  if (millis() - last >= 10000) {
    last = millis();
    float t = dht.readTemperature(), h = dht.readHumidity();
    if (!isnan(t) && !isnan(h)) {
      char json[96];
      snprintf(json, sizeof json, "{\"temperature\":%.1f,\"humidity\":%.0f}", t, h);
      mqtt.publish(topic("telemetry").c_str(), json);   // QoS 0: PubSubClient limit
    }
  }
}

function node · alarm state machine
// Inputs: topic "flame" (payload true/false), "ack", "shelve", "unshelve", "tick"
const SHELVE_MS = 15 * 60 * 1000;
let st = context.get('st') || { state: 'NORMAL', active: false, shelvedUntil: 0 };
const now = Date.now();

// Shelf expired: re-annunciate if the condition is still present
if (st.state === 'SHELVED' && now >= st.shelvedUntil) {
    st.state = st.active ? 'UNACK' : 'NORMAL';
}

switch (msg.topic) {
  case 'flame':
    st.active = msg.payload === true;
    if (st.state === 'SHELVED') break;
    if (st.active) {
      if (st.state === 'NORMAL' || st.state === 'RTN_UNACK') st.state = 'UNACK';
    } else {
      if (st.state === 'UNACK') st.state = 'RTN_UNACK';
      else if (st.state === 'ACKED') st.state = 'NORMAL';
    }
    break;
  case 'ack':
    if (st.state === 'UNACK') st.state = 'ACKED';
    else if (st.state === 'RTN_UNACK') st.state = 'NORMAL';
    break;
  case 'shelve':
    st.state = 'SHELVED';
    st.shelvedUntil = now + SHELVE_MS;
    node.warn('Flame alarm shelved for 15 min');   // shelving must be logged
    break;
  case 'unshelve':
    if (st.state === 'SHELVED') st.state = st.active ? 'UNACK' : 'NORMAL';
    break;
}

context.set('st', st);
msg.payload = st.state;
msg.alarm = st;
return msg;

A token-protected HTTPS ingestion endpoint storing readings in SQLite, plus a history query, fed by an HTTPS POST from the ESP32-C3. Session S9. Runs locally only.

app.py · pip install flask · Python 3.9+
import os, sqlite3, hmac
from datetime import datetime, timezone
from flask import Flask, request, jsonify, g

DB = os.environ.get("IOT_DB", "readings.db")
API_TOKEN = os.environ["IOT_API_TOKEN"]        # never hard-code secrets

app = Flask(__name__)

def db():
    if "db" not in g:
        g.db = sqlite3.connect(DB)
        g.db.execute("PRAGMA journal_mode=WAL")
    return g.db

@app.teardown_appcontext
def close_db(exc):
    conn = g.pop("db", None)
    if conn is not None:
        conn.close()

def init_db():
    with sqlite3.connect(DB) as c:
        c.execute("""CREATE TABLE IF NOT EXISTS readings(
            id INTEGER PRIMARY KEY, device_id TEXT NOT NULL, ts TEXT NOT NULL,
            temperature REAL, humidity REAL, flame INTEGER)""")
        c.execute("CREATE INDEX IF NOT EXISTS idx_dev_ts ON readings(device_id, ts)")

def authorised():
    header = request.headers.get("Authorization", "")
    return header.startswith("Bearer ") and \
        hmac.compare_digest(header.removeprefix("Bearer "), API_TOKEN)

@app.post("/api/v1/readings")
def ingest():
    if not authorised():
        return jsonify(error="invalid or missing token"), 401
    data = request.get_json(silent=True)
    if not isinstance(data, dict) or "device_id" not in data:
        return jsonify(error="JSON body with device_id required"), 400
    try:
        t, h = float(data["temperature"]), float(data["humidity"])
    except (KeyError, TypeError, ValueError):
        return jsonify(error="temperature and humidity must be numbers"), 400
    ts = datetime.now(timezone.utc).isoformat(timespec="seconds")
    conn = db()
    conn.execute("INSERT INTO readings(device_id, ts, temperature, humidity, flame) "
                 "VALUES (?, ?, ?, ?, ?)",                  # parameterised: no SQL injection
                 (str(data["device_id"]), ts, t, h, int(bool(data.get("flame", False)))))
    conn.commit()
    return jsonify(status="stored", ts=ts), 201

@app.get("/api/v1/devices/<device_id>/readings")
def history(device_id):
    if not authorised():
        return jsonify(error="invalid or missing token"), 401
    limit = min(request.args.get("limit", 100, type=int), 1000)
    rows = db().execute("SELECT ts, temperature, humidity, flame FROM readings "
                        "WHERE device_id = ? ORDER BY ts DESC LIMIT ?",
                        (device_id, limit)).fetchall()
    return jsonify([dict(ts=r[0], temperature=r[1], humidity=r[2], flame=bool(r[3]))
                    for r in rows])
